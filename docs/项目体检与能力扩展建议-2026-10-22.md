# 项目体检与能力扩展建议

> 日期：2026-10-22
> 基线：`master@0e62b5c` + 36 个未提交改动（editor 转场/插件、ChatStudio、oss.js）
> 方法：只写代码里能验证的事，行号可直接跳转；无法在本机验证的（线上库规模、外部 cron）单独标「待确认」。

---

## 0. 一句话结论

功能已经不少了，现在拖后腿的不是"缺功能"，是三件事：

1. **请求路径上的重复计算**——列表页每张图都在重算哈希、写数据库；
2. **没有运维底座**——不备份、不记审计、不记成本、`/health` 只有一个 `ok:true`；
3. **没有"对外"的那一面**——对内能管、能生成、能剪，但没有给客户看的交付物。

前两条是止血，第三条是新增收入/口碑的地方。

## 2. 可优化项

### P0 · 本周可做，收益立刻能感觉到

#### 2.1 缩略图每次请求重算两个哈希并写库

**证据**：`src/api.js:4342` 读文件 → `src/export-tag.js:112` 里 `sha256 + md5 + UPSERT export_registry`。

**影响**：一屏 60 张图 = 60 次全量哈希 + 60 次数据库写（WAL 持续增长）。缩略图没有 `ETag`/`304`，用户回滚、切换筛选都会重付一次。这是当前列表滚动手感的主要成本，而且 `export_registry` 被缩略图哈希污染。

**改法**（约 1 小时）：

1. 进程内 LRU：key = `fid + mtime + size`，命中直接跳过 `registerVisibleImageHashes`；
2. 响应加 `ETag`（用 `fid + mtime + size` 派生）与 `If-None-Match` → 304；
3. `sendFile` 用 `fs.createReadStream` 替代 `readFileSync`。

**预期**：列表接口 CPU 降一个量级，重复访问带宽接近 0。

#### 2.2 没有自动备份

**证据**：`src/db.js:87`；`migrate.js:14` 的 `backupDb()` 只在手动迁移时用。

**影响**：`material.db` 是唯一权威源。磁盘坏、误删、迁移写坏，就是全丢。且回收站 3 天自动清理是**物理删除**，没有二次兜底。

**改法**（约 2 小时）：启动后每小时 `db.backup()`（better-sqlite3 自带在线备份，不锁库）到 `backups/`，保留 7×24 份 + 每日 1 份保留 30 天；提供 `scripts/restore-backup.js`。**这一项优先级高于本文其它所有优化。**

#### 2.3 444 MB 静态资产

**证据**：`web-pro/public/models/` 与 `web-pro/public/assets-3d/` 内容完全重复，三个 74 MB 的 GLB。

**影响**：首次进工作台/预览 3D 直接拉 74 MB；部署包体、备份、镜像全被拖大；无压缩、无 LOD。

**改法**：`gltf-transform` 跑 Draco/meshopt + 纹理压缩，74 MB 通常能到 3–8 MB；删掉重复目录；GLB 走按需加载（<model-viewer> 本身支持 `loading="lazy"`）。

#### 2.4 27 个 `.next-build` 目录

**影响**：磁盘几个 GB；更重要的是**构建版本歧义**——今天已经因此误判过一次"改动没生效"。

**改法**：保留最近 2 个，其余清理；在 `service-hub` 的一键重建里加"构建前清理旧产物（保留 2 份）"。

#### 2.5 `/health` 太薄

**证据**：`src/api.js:1390` 只返回 `{ok:true, service, ts}`。

**改法**：扩成运维探针——三个队列的 pending/running/failed 数、DB 大小与 WAL 大小、数据盘余量、各供应商最近一次成功时间、最近 1 小时失败任务 Top3。故障时不用登机器猜。

### P1 · 两周内

#### 2.6 关键词搜索是全表 LIKE + 两遍扫描

**证据**：`api.js:786`（`file_name LIKE '%x%'` + 子查询 `tag_dict.label LIKE`），`api.js:796` 再跑一次 `COUNT(*)`。

**影响**：前置通配符用不上索引；数据量上万后每次搜索都是全表 + 标签表 join，翻页再算一次总数。

**改法**：建 FTS5 虚拟表（`file_name`、标签 `label/dir`、AI 描述），搜索走 `MATCH`；`COUNT` 用同一条件只算一次或缓存 5 秒；纯标签筛选仍走索引。改动集中在 `buildAssetFilters`，风险可控。

#### 2.7 相似搜索把整库载入内存

**证据**：`src/vector.js:214` 一次 `SELECT ... FROM assets LEFT JOIN asset_vectors` 全量 `.all()`，再在 JS 里算余弦。

**影响**：素材数线性放大；详情页每次打开都可能触发一次全表扫描（配合 `sort=recommend` 的 `EXISTS` 子查询更明显）。

**改法**（按成本递增）：① 候选集先按 `space` + `dominant_color` 粗筛，再算向量；② 离线预计算每张图的 Top-50 邻居存表，详情页直接读；③ 素材到十万级再考虑 `sqlite-vec`。

#### 2.8 SQLite 只设了 WAL 和 foreign_keys

**证据**：`scripts/migrate.js:335-336`。

**改法**：补 `busy_timeout=5000`、`synchronous=NORMAL`、`cache_size=-64000`（64 MB）、`mmap_size=256MB`。WAL 下 `synchronous=NORMAL` 是官方推荐组合，写入吞吐明显提升，崩溃最多丢最后一个事务。

#### 2.9 AI 队列单条串行 + 固定 2 秒轮询

**证据**：`src/ai-tasks.js:971` `LIMIT 1`，`tick()` 每 2 秒一次，一次只处理一条。

**影响**：批量生成 20 张图时，排队时间 = 20 × 单张耗时 + 轮询空转；同时上游供应商的并发能力被浪费。

**改法**：可配置并发槽（默认 2–3，按供应商分组限流）；失败带指数退避与 `attempts` 计数；队列空时用 `setTimeout` 拉长到 10 秒，有任务再回 2 秒。

#### 2.10 multipart 直传整包进内存，上限 2 GB

**证据**：`src/stream-upload.js:548` 调 `readRequestBuffer`，`src/ingest.js:86` 把整个 body `Buffer.concat`。

**影响**：任何人 POST 一个 1.5 GB 视频就能把 Node 进程内存打爆（Node 单 Buffer 上限 2 GB）。当前靠 watchdog 拉起，但正在跑的任务全断。

**改法**：`content-length > 64 MB` 直接 413，要求走分片（已有 `handleChunkUpload`）；或把 multipart 流式落盘再处理。

#### 2.11 前端单包、无懒加载、无压缩

**证据**：`App.vue` 静态 import 四个视图；`web-pro/dist/assets/index-*.js` 697 KB；`server.js` / `web-pro/server.cjs` 都没有 gzip。

**改法**：`defineAsyncComponent` + 路由级拆分（Library/Studio/Settings 各自成 chunk）；静态响应加 gzip/br（或前置 nginx 开 `gzip on`）。首屏 JS 可从 697 KB 降到 200 KB 级。

#### 2.12 `api.js` 巨石与四套模型表

不是"必须改"，是"改之前先别加"：`api.js` 246 个分支已经让每次改动都要读 7 千行；`models-contract.js` 4,314 行维护四套模型表，靠 `reconcile` 对齐。

**建议**：不重写，做**增量抽取**——按域把 handler 搬到 `src/routes/{assets,gen,admin,media,chat}.js`，`api.js` 只留一张 `[method, regex, handler]` 路由表。每搬一个域跑一次现有回归。四套模型表先加一张"投影视图"读侧统一，写侧维持现状。

#### 2.13 47 处静默 `catch {}`

关键路径（入库、导出、缩略图、AI 回调）的静默失败会让问题延后暴露。建议至少加 `logger.warn` 带上 fid/路径，非关键清理逻辑可以保留静默。

## 3. 可以新增的能力

按"价值 ÷ 成本"排序。前三个是我认为真正值得做的。

### A. 客户交付画廊（分享链接）— 最推荐

**为什么**：现在整个系统是"对内"的：入库、打标、生成、剪辑。但设计师最终要把东西给客户看。目前只能导出图片再发微信，没有品牌感、不知道客户看没看、也没法收回。

**最小可用范围**：

- `POST /share` 选一组素材/一个剪辑工程 → 生成 `share_token`；
- 公开只读页 `/s/<token>`：瀑布流 + 大图 + 空间分组，移动端优先；
- 选项：4–6 位访问口令、有效期（7/30/永久）、是否允许下载、右下角品牌水印（复用 sharp）、禁止右键；
- 访问统计：谁在什么时候看了哪些图、停留时长、下载次数；
- 后台可随时失效链接。

**成本**：后端 1 天（表 + 3 个接口 + 鉴权旁路），前端 1 天（一个独立只读页面，不进主包）。**风险点**：公开路由必须与现有 `VIEWER_WHITELIST` 完全隔离，只认 token，绝不复用登录态。

### B. 方案册 / 提案 PDF

**为什么**：客户看完图，下一步就要"一页一个空间 + 材质说明 + 风格说明"的册子。现在只能人工 PPT。

**最小可用范围**：选素材 → 选模板（封面/空间页/材质页/尾页）→ 自动取标签生成文案 → 服务端排版出 PDF（`pdfkit` 或 headless Chromium 截图）→ 下载。第一版可以只做 3 个模板、A4 横版。

**成本**：2–3 天。依赖 A 的"分组"数据结构，建议 A 之后做。

### C. 自然语言找图（真语义检索）

**为什么**：现在是关键词 LIKE + 68 维手工特征。"奶油风 小户型 客厅 无主灯 木饰面"这种组合，LIKE 匹配不到，手工特征也表达不了"感觉"。

**做法**：中文 CLIP（如 Chinese-CLIP ViT-B/16）离线给每张图算 512 维向量，文本侧同一空间编码。`asset_vectors` 表已经存在，加 `model='clip_zh_v1'` 即可并存，不影响现有 68 维逻辑。查询时先向量召回 Top-200，再用现有标签/主色做重排。

**成本**：模型服务 1 天（Python sidecar 或 onnxruntime-node）+ 批量回填 1 晚 + 接口 0.5 天。**注意**：需要先确认线上素材规模，超过 10 万再考虑 ANN 索引，否则暴力算就够。

### D. 成本与用量看板

**为什么**：现在生成一张图、一段视频花的是真金白银，但系统里没有任何一处记录花了多少。供应商换钥匙、模型涨价、某条工作流空转，全靠人肉发现。

**做法**：在 `gen/adapters` 与 `vlm` 的出口统一埋点，落 `usage_log(provider, model, kind, units, unit_cost, task_id, actor, ts)`；`usage_log` 按天聚合出"今日花费 / 本月花费 / 单张均价 / 失败浪费"。**先记账再谈优化**，这张表也是后面做预算告警的基础。

**成本**：1.5 天。与审计日志共用一套写入封装，建议一起做。

### E. 剪辑 AI runner 补齐

`clip-ai.js` 已经支持 `subtitle / matting / beauty_pro / face_reshape / upscale` 五种类型，队列、面板、产出下载全通，`data/clip-ai-runners/` 只有 2 个脚本。**这不是新能力，是"铺好路没通车"**。

优先级：字幕（faster-whisper，离线、稳定、用户感知最强）> 抠像（RVM/BiRefNet）> 超分。每接一个只要写一个 runner 文件，不动主链路。

### F. 批注与评审（团队协作）

在图上圈选 + 文字评论 + @人，用于"这张沙发换掉""这个角度的灯太亮"。当前只有 admin/viewer 两种角色，没有协作概念。**建议等 A（对外交付）跑通后再做**，因为客户评审和内部评审可以共用一套批注数据模型。

### G. 冷热分层

`nasstore.js` 已有 NAS 归档，但目前只归档原图，且是同步 `copyFileSync` 在定时器里跑。素材到几万张后，建议：热数据（最近 90 天 / 被引用过）留本地，冷数据原图只留 NAS + 本地缩略图，访问时按需回迁。

## 5. 现在不建议做的

- **全量重写 `api.js`**：7,500 行里全是业务细节和踩过的坑（`decodeParamLoose`、`ML_SAVED_`、rev CAS），重写必然回归。只做增量抽取。
- **上 Postgres / Redis**：单机 SQLite + WAL 在这个量级完全够用，换存储只会把"单机事务"变成"分布式一致性"问题。
- **本地/云端双向同步**：已经明确只做"云端只读快照"，这个决定是对的，别回头。
- **多租户**：当前是"一个工作室一个库"，加租户会把 57 张表全改一遍，收益不明。

## 6. 需要你确认的四件事

1. **线上库规模**：素材总数、`assets`/`derivatives` 行数、`material.db` 大小。这决定 2.6/2.7 是"下周做"还是"下季度做"。
2. **外部有没有 cron 在备份**：如果 NAS 上有定时 `cp`，2.2 可以降级为"补一个应用内校验"。
3. **30002 前面有没有 nginx**：有的话 2.11 的 gzip 不用改代码。
4. **交付优先形态**：客户链接（A）还是 PDF 方案册（B）先做？我的判断是先 A，因为它同时解决"给客户看"和"拿反馈"。
