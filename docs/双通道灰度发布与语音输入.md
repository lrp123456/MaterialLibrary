# 双通道灰度发布与语音输入（A/B 灰测）

> 定稿：2026-10-23。本文是「30003 灰测 → 30002 正式」和「本地语音输入」的唯一操作说明。
> 端口是铁律，任何脚本、文档、口头沟通都以这张表为准。

## 1. 通道矩阵

| 通道 | 服务端 API | 前端入口 | 前端产物 | 数据目录 | 进程归属 |
| --- | --- | --- | --- | --- | --- |
| 正式 | `30001` | `http://127.0.0.1:30002/` | `web-pro/dist` | WSL `~/.dsh-material-library` | WSL + `scripts/watchdog.sh` 守护 |
| 灰测 | `30000` | `http://127.0.0.1:30003/` | `web-pro/dist-gray` | Windows `%USERPROFILE%\.dsh-material-library-gray` | Windows，`scripts/gray-release.js` 拉起 |
| 剪辑子应用 | —— | 两个入口都走 `/editor` → `3010` | `editor/apps/web` | 共用 | 共用（灰测暂不隔离剪辑） |

两条通道**共用同一份源码**，区别只在端口、构建产物目录和数据目录。

## 2. 日常开发流程

```text
改代码  →  node scripts/gray-release.js          # 构建 dist-gray + 重启灰测
        →  打开 http://127.0.0.1:30003 验证
        →  设置 → 双通道灰度发布 → 「发布到正式版」
        →  30002 换新前端，30001 自重启加载新后端代码
```

对应快捷方式：

- `启动灰测通道.bat`：构建 + 拉起 30000/30003（参数见 bat 内注释）
- `停止灰测通道.bat`：停掉灰测两个进程
- `node scripts/gray-release.js --no-build`：只重启灰测进程（改了 `server.js` / `src/*.js` 时用）
- `node scripts/gray-release.js --sync-data`：重新从正式库拉一份数据库快照
- `node scripts/gray-release.js --status`：只看四条端口的存活情况
- 服务面板（`启动服务面板.bat` → 3790）里也有「灰测服务端 (30000)」「灰测 Web 端 (30003)」两个条目

## 3. 灰测通道的数据模型

灰测不是「另起一套空库」，也不是「和正式共用一份库」，而是：

1. **数据库**：首次启动时把正式库 `material.db`（含 `-wal`/`-shm`）复制一份到
   `%USERPROFILE%\.dsh-material-library-gray`。之后灰测的写入只落在副本里，正式库不受影响。
2. **图片缓存**：`cache` 目录用**符号链接**指向正式缓存
   （`\\wsl.localhost\smu\home\lrp\.dsh-material-library\cache`）。正式缓存已经 52GB，
   不可能复制；链接后灰测能看到全部素材图，新生成的图也会写回同一位置（文件名按 fid 唯一，不冲突）。
   需要 Windows 开发者模式（本机已开启）；链接失败时脚本会打印 `mklink /D` 手动命令。
3. **后台 worker**：灰测实例以 `APP_CHANNEL=gray` 启动，**不跑** AI 任务、快捷处理、
   夜间重打标、回收站清理、NAS 归档、restart 标记轮询。它只提供读写 API 和联调，
   避免两个进程抢同一批任务。

代价说明：灰测是正式库的**快照**，正式端新入库的素材在灰测里看不到，除非重新 `--sync-data`。
这是为了「灰测绝不污染正式数据」刻意做的取舍。

### 3.1 剪辑台（/editor）在灰测通道的两个前提

1. **必须 HTTPS**。剪辑台的素材存储走 OPFS、导出走 WebCodecs，浏览器只在**安全上下文**里开放这两个 API。
   `127.0.0.1` 天然算安全上下文，但用局域网 IP（`192.168.1.59:30003`）走 HTTP 就不算，
   页面顶部会出现橙色警告「不是安全上下文，没有启用 OPFS / WebCodecs」，此时建工程会直接失败。
   灰测脚本启动时会自动把正式端的 `server.crt` / `server.key` 复制到
   `%USERPROFILE%\.dsh-material-library\tls`，30003 随即同端口开启 HTTPS（HTTP 导航自动 302 到 HTTPS）。
   证书与正式端共用同一套本地 CA，**装过一次的设备不用重装**；没装过的设备访问
   `https://<host>:30003/mls-ca.crt` 下载安装即可。
2. **工程不跨 origin 共享**。OpenCut 的工程存在浏览器 IndexedDB + OPFS 里，按 origin 隔离：
   `30003` 与 `30002` 是两个 origin，所以在 30002 里建好的本地工程**不会**出现在 30003。
   要在灰测里验证真实工程，用「导出工程 / 导入工程」（`.mlsclip`），或者走云端快照
   （灰测库是正式库副本，复制时点之前的快照两边都有）。

灰测复用正式端的 Next 进程（`3010`），所以剪辑壳代码只有一份；`/editor-api` 会代理到 30000，
即剪辑相关的读写落在灰测库副本里。

## 4. 发布到正式版（内部步骤）

点「发布到正式版」后，灰测后端（30000）按顺序执行：

1. **检查正式通道**：`GET 30001/health` 必须通，否则直接失败并提示先启动正式服务。
2. **构建正式前端**：`vite build --outDir web-pro/dist --emptyOutDir`。
   项目在 C: 盘，WSL 通过 `/mnt/c` 读同一份文件，所以静态产物构建完**立刻生效**。
   同时写入 `dist/build-info.json`（提交号、构建时间、未提交改动数）。
3. **重启正式后端**：`POST 30001/api/system/restart`（仅本机 + `x-ml-internal: restart` 头）。
   正式端校验 `watchdog.pid` 存活后返回 202，1.2 秒后 `process.exit(0)`，
   由 `scripts/watchdog.sh` 重新拉起，加载最新的 `server.js` / `src/*.js`。
4. **重启正式前端网关**：`POST 30002/__ml/restart`，同理退出后由 watchdog 拉起，
   用于让 `web-pro/server.cjs` 的改动生效（只改前端代码时其实不需要）。
5. **核验**：比对 `dist/build-info.json` 的提交号与当前工作区是否一致，不一致标红。

发布期间的可见影响：构建的 5~15 秒内正式页面可能短暂 404（`dist` 被清空重写）；
两个服务各重启一次，每次 2~5 秒。发生在本地开发机上，可接受。

### 首次启用需要一次手动重启（重要）

正式端现在跑的还是**旧代码**，里面没有 `/api/system/restart` 和 `/__ml/restart`。
所以第一次点「发布到正式版」时，构建会成功，重启步骤会失败并提示：

> 正式端若是旧代码，请手动执行一次「停止素材库.bat → 启动素材库.bat」后重试

手动重启一次后，正式端就有了自重启接口，之后所有发布全自动。
之所以要这样，是因为 `wsl.exe` 被安全策略列入程序黑名单，Windows 侧无法直接重启 WSL 里的进程。

### 回滚

`web-pro/dist` 每次构建前 vite 会 `--emptyOutDir` 清空，所以没有自动保留上一版。
需要回滚时：`git checkout <上一个好提交> -- web-pro/src` → 重新点发布（或 `--no-build` 前先手动构建）。
如只是后端出问题：`git checkout <commit> -- server.js src/`，然后点一次「发布到正式版」
（勾选重新构建也可以，但没有前端改动可以不勾）。

## 5. 语音输入（FunASR / SenseVoice）

### 5.1 用了什么

- 模型：**SenseVoice-Small（int8）**，FunASR 生态模型（阿里达摩院），中英日韩粤 + 标点 + ITN。
- 推理后端：`sherpa-onnx`（同一个模型权重，C++/ONNX 实现，单 wheel、不需要 torch）。
  FunASR 官方 Python 包在 Windows + Python 3.13 上要现场编译 `numpy`/`kaldi-native-fbank`，
  且会拉 `torchaudio` 和已装的 torch 抢版本，所以没走官方包。
- 服务：`scripts/asr/asr_server.py`
  - HTTP `127.0.0.1:10095`：`GET /health`、`POST /transcribe`（WAV 或 16k PCM16）
  - WS `127.0.0.1:10096`：二进制 PCM16 帧 + JSON 控制帧（`start` / `flush` / `end`）
- 网关：`src/asr.js`，把 `/api/asr/status`、`/api/asr/transcribe`、`/api/asr/stream` 挂到现有 HTTP 服务上，
  复用登录会话鉴权；前端只跟同源 `/api/*` 说话，局域网/公网访问不需要额外开端口。
- 前端：`web-pro/src/components/VoiceInputButton.vue`，App.vue 里全局挂载，右侧悬浮麦克风。
  **不需要逐个输入框改造**：它记住「最后聚焦的可编辑元素」，识别完直接把文字插回去
  （原生 setter + `input` 事件，Vue 的 `v-model` 能同步），所以对话输入框、提示词、搜索框、
  设置页输入框全都能用；找不到输入框时退回剪贴板并提示。

### 5.2 是否实时

- **准实时**：说话过程中每约 1.1 秒给一次 `partial` 预览；检测到 0.55 秒停顿就提交一句
  （`commit`）；松手后 0.3 秒内出整段 `final`。
- 实测（CPU，2 线程）：5.6 秒中文音频整段解码 **290ms**；7.2 秒英文 **350ms**。
  即约 20 倍实时速度，边录边转不会积压。
- **逐字流式**（每个字都实时跳动）需要换 `paraformer-zh-streaming` 流式模型（约 1GB，
  600ms chunk），服务端协议已经支持按 chunk 出结果，只是当前模型是整段解码。
  需要时把模型换成 streaming 版并在 `asr_server.py` 里改用 `OnlineRecognizer` 即可，
  前端不需要改。
- 浏览器要求**安全上下文**：`127.0.0.1`/`localhost` 天然满足；局域网 IP 走 HTTP 时麦克风会被禁，
  需要用 30002 已配置的 HTTPS 入口（`https://<host>:30002/`，先装 `/mls-ca.crt`）。

### 5.3 启用步骤

1. 双击 `启动语音识别.bat`（首次会自动加载模型，约 1.5 秒；日志在控制台）。
   也可以在服务面板里点「语音识别 (FunASR)」启动，或设 `ASR_PYTHON` 指定 python。
2. 打开 30003（或 30002），右侧出现麦克风按钮；点一下开始，再点一下停止并插入。
3. 状态自检：`curl http://127.0.0.1:10095/health`，或页面 `GET /api/asr/status`。

模型目录默认 `%USERPROFILE%\.dsh-material-library\models\asr\sherpa-onnx-sense-voice-...`，
可用 `ASR_MODEL_DIR` 覆盖。HTTP/WS 端口分别用 `ASR_HTTP_PORT` / `ASR_WS_PORT` 覆盖。

### 5.4 正式端（WSL）如何连到 Windows 上的 ASR

本机 `.wslconfig` 是 `networkingMode=Mirrored` + `hostAddressLoopback=true`，
WSL 里的 `127.0.0.1:10095/10096` 能直接打到 Windows 上监听 `0.0.0.0` 的 ASR 服务，
所以正式后端默认用 `ASR_HTTP_URL=http://127.0.0.1:10095` / `ASR_WS_URL=ws://127.0.0.1:10096` 就能用。

如果哪天改回 NAT 模式（WSL 看不到 Windows 回环），在 `.env` 里改成 Windows 的局域网地址：

```ini
ASR_HTTP_URL=http://192.168.1.59:10095
ASR_WS_URL=ws://192.168.1.59:10096
```

并放行 Windows 防火墙入站 TCP 10095/10096。改完重启正式后端。

## 6. New API 渠道（newapi.naite.cc）

| 项 | 值 |
| --- | --- |
| 接入点 id | `newapi` |
| Base URL | `https://newapi.naite.cc/v1`（可用 `NEWAPI_BASE_URL` 覆盖） |
| 能力 | `newapi_chat`（`/chat/completions`） |
| 模型 | `gemini-4-argon`，目录 id `gemini_4_argon`，展示名「Gemini 4 Argon」 |
| 密钥 | `.env` 的 `NEWAPI_API_KEY`（轮换池 `NEWAPI_API_KEYS`，逗号分隔） |

模型契约 `capability_id=newapi_chat`，`resolveLiteLlmChatConfig` 会识别为直连接入点，
不再经过本地 LiteLLM。对话页模型下拉里选「Gemini 4 Argon」即可；实测：

```bash
curl -s -X POST http://127.0.0.1:30000/api/gen/chat \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"model":"gemini-4-argon","prompt":"用一句中文回答：你是什么模型？"}'
# → 我是谷歌研发的大型语言模型，名叫 Gemini 4 Argon。
```

密钥只从 `.env` 读，不落 SQLite，管理台只显示指纹掩码。

## 7. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 30003 打不开或 502 | 灰测进程没起 / 30000 未就绪 | `启动灰测通道.bat`，看 `~/.dsh-material-library-gray/logs/{api,web}.log` |
| 灰测页面图片全裂 | cache 符号链接失败（未开开发者模式） | 用管理员执行 `mklink /D "<gray>\cache" "\\wsl.localhost\smu\home\lrp\.dsh-material-library\cache"` |
| 30003 剪辑台顶部橙色警告 / 建工程失败 | 没有 HTTPS，非安全上下文 | 确认 `%USERPROFILE%\.dsh-material-library\tls\server.crt` 与 `.key` 存在（脚本会自动从正式端复制），重启 30003；用 `https://` 打开 |
| 30003 里看不到 30002 的剪辑工程 | 不同 origin 的 IndexedDB 互相隔离 | 用「导出工程 / 导入工程」，或走云端快照 |
| 30003 打开工程白屏 / Application error | 浏览器拿不到 WebGPU/WebGL 上下文 | 换 Chrome/Edge 并开启硬件加速；远程桌面/无 GPU 环境会初始化失败 |
| 发布卡在「重启正式后端」 | 正式端是旧代码 / 没有 watchdog | 手动「停止素材库.bat → 启动素材库.bat」一次，再发布 |
| 发布报「正式后端不可达」 | 30001 没在跑 | 先启动正式服务 |
| 麦克风按钮灰色 | ASR 服务没起 / 未登录 / 非安全上下文 | 起 `启动语音识别.bat`；用 127.0.0.1 或 HTTPS |
| 语音只出预览不出最终文字 | 旧版 `src/asr.js` 把控制帧当二进制发给 Python | 确认 `onMessage` 里文本帧转 string（已修） |
| 识别慢 | CPU 线程太少 / 音频太长 | `ASR_THREADS=4`；「按住说话」场景单段建议 < 30 秒 |
