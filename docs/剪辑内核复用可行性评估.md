# 剪辑内核复用可行性评估

> 版本：v1.0（2026-10-20）
> 对象：剪映专业版 11.6.0.14552（本机实装）+ OpenCut Classic（本机源码）
> 问题：**我们的剪辑板块能否直接用他们的内核，UI 做适配改造？**
> 结论先行：**剪映不能；OpenCut 能，但"整块拿内核"是伪命题——真正能拿来的是它的 GPU 渲染器 `opencut-wasm`。**

---

## 0. 一页结论

| 对象 | 能否复用内核 | 判定依据 | 建议 |
|---|---|---|---|
| **剪映 11.6** | ❌ 不能 | 原生 Qt6+CEF；引擎是 500 MB 级闭源 DLL；**无 SDK/头文件/ABI**；唯一可编程面 `hubcli` 只有 3 条素材命令；**v11 草稿已真加密**（熵 7.946） | 只作为交互与导出预设的参考，不做任何代码/进程级复用 |
| **OpenCut Classic** | ✅ 能，分粒度 | MIT；内核层 **0 个 React 依赖**；渲染器 `opencut-wasm` 是独立 npm 包，暴露 6 个函数 | **先只换渲染内核（L0）**，UI 与模型全不动；效果达标再考虑移植 core |

一句话：**"用他们的内核 + 改我们的 UI"这个方向成立，但成立的是 OpenCut，不是剪映；而且第一步不该是搬内核，是先换掉我们那块 Canvas 2D 合成器。**

---

## 1. 先定义"复用"的四种粒度

"用内核"是个模糊说法。拆成四层，后面所有判断都按这个尺子量：

| 粒度 | 含义 | 我们保留什么 | 要改什么 |
|---|---|---|---|
| **L0 渲染内核** | 只换合成器（像素怎么合成） | 模型、UI、命令栈、服务端导出 | `compositor.js` → WASM/GPU |
| **L1 内核移植** | 换数据模型 + 命令栈 + 渲染器 | UI、服务端、素材库 | `model.js/store.js/compositor.js` 全换 |
| **L2 整块替换** | 用对方整个编辑器（含 UI） | 只保留壳与素材注入 | 前端编辑器整体换掉 |
| **L3 只借架构** | 不拿代码，照抄分层与算法 | 全部 | 按对方结构重写 |

> 注：**没有"只换内核、UI 一点不改"的免费午餐**。渲染器可以做到（L0）；数据模型一换，UI 绑定的字段就全变（L1 起 UI 必须跟着改）。

## 2. 剪映 11.6.0.14552 逆向

### 2.1 安装画像

| 项 | 事实 |
|---|---|
| 安装路径 | `%LOCALAPPDATA%\JianyingPro\Apps\11.6.0.14552` |
| 总体积 | **3.4 GB**（`Resources/` 817 MB、`cef/` 309 MB） |
| 版本 | 11.6.0.14552 |
| 工程目录 | `%LOCALAPPDATA%\JianyingPro\User Data\Projects\com.lveditor.draft\<草稿名>\` |

### 2.2 架构判定：Qt6 + CEF，不是 Electron

目录里同时出现三套 UI 运行时：

- **Qt 6**：`Qt6Bodymovin.dll`、`QtQuick/`、`QtQml/`、`Qt5Compat/` —— 主界面。
- **CEF（Chromium 嵌入式框架）**：`cef/` 309 MB、`CefCreator.dll`、`PlatinumWebView.dll`、`data/icudtl.dat` —— 内嵌网页（活动页/模板/会员）。
- **Lynx**：`lynx.dll` 22 MB、`lynx_core.js` —— 字节自家跨端 UI 框架，部分面板用它渲染。

**这意味着**：剪映没有一层"可被外部调用的 Web 引擎"，UI 是 C++ 直绘 + 内嵌浏览器的混合体。想复用 UI，等于复用它的 C++ 窗口与消息循环。

### 2.3 引擎边界：体积即证据

| DLL | 体积 | 推断职责 |
|---|---|---|
| `VECreator.dll` | **260 MB** | 视频编辑核心（Video Editing Creator） |
| `cccreator.dll` | 152 MB | 创作/合成管线 |
| `lens.dll` | 85 MB | 特效/滤镜/镜头 |
| `videoeditor.dll` | 70 MB | 时间线/轨道/片段运算 |
| `avcodec-61.dll` | 19 MB | FFmpeg 编解码 |
| `audioeffect.dll` | 14 MB | 音频效果 |
| `onnxruntime_providers_cuda.dll` | 696 MB | AI 推理（CUDA） |
| `vm_sdk/` | 6 MB | 视频模型 SDK |
| `smart_cut.ofx.bundle/` | 592 KB | **OpenFX 插件包**（行业标准插件格式） |

**关键结论**：编辑能力全部沉在 C++ 里，**没有任何 `.h` / `.lib` / `.def` / IDL / 文档**。目录里只有运行时 DLL，没有可供第三方链接的导入库。这不是"没文档"，是**从构建上就没打算给外部调用**。

`Service/` 目录只有 `jyshellext.dll`（资源管理器右键"用剪映打开"的 Shell 扩展）+ 一个 MSIX 包，**没有 IPC 服务、没有本地 API 端口**。

### 2.4 唯一可编程面：`hubcli`，只有 3 条命令

`Resources/agent_runtime_env/` 里有字节给自家 AI Agent 准备的运行时，含 `bin/hubcli`、`cli/hubcli/{contracts.json,sdk.mjs,cli.mjs}`。

`contracts.json` 声明的协议是 `custom-agent.hub-cli.v1`，**全部命令只有 3 条**：

| 命令 | 权限 | 说明 |
|---|---|---|
| `asset.list` | readonly | 列出当前画布/当前 Run 的素材（只返回 asset_id 与元数据，**不给本地路径**） |
| `asset.get` | readonly | 按 asset_id 取单个素材 |
| `asset.import` | write | 导入内联文本或受信本地资源到托管素材库 |

而 `cli.mjs` 开头写明：

> 参数和回执仅用于 Shell I/O；**业务身份、授权和交付由 Host 持有**。

即：**必须有正在运行的剪映宿主进程 + 宿主授权**，且这套接口只能"导入素材/查素材"，**不能建时间线、不能加片段、不能导出**。

推论：`hubcli` 是给剪映内部 AI 功能用的素材接口，**不是给外部系统做剪辑自动化的 API**。

### 2.5 草稿格式：v11 已经真加密

这是本次逆向最重要的发现，直接推翻上一版计划里"用草稿当交换格式"的设想。

对一份真实草稿取样：

| 文件 | 大小 | 状态 |
|---|---|---|
| `draft_content.json` | 3,936 B | **加密**（非 JSON） |
| `draft_content.json.bak` | 3,936 B | **加密**，且与上面**密文不同** |
| `draft_meta_info.json` | 3,420 B | **加密** |
| `draft_virtual_store.json` | 355 B | 明文 JSON |
| `timeline_layout.json` | 206 B | 明文 JSON |

量化判定（base64 解码后 2,950 字节）：

| 指标 | 数值 | 含义 |
|---|---|---|
| 香农熵 | **7.946 / 8.0** | 接近理想随机，无任何结构 |
| 两份文件异或后熵 | **7.931** | 密钥流不同（每次加密带不同 IV/nonce） |
| 异或后零字节占比 | 0.4% | 不是"固定 key 的简单 XOR 混淆" |
| zlib / gzip 头 | 均不匹配 | 不是压缩后加密的常见容器 |

**结论：这是 AES 级别的真加密，不是 XOR/Base64 混淆。** 密钥在原生侧（`metasecml.dll` / `sscronet.so` 这类安全模块），外部拿不到。

后果：

1. 你**生成的草稿剪映打不开**（写不出合法密文）。
2. 你**读不了用户已有的草稿**（解不开）。
3. 上一版计划里"以剪映草稿格式作为导入/导出桥梁"的设想，在 11.x 上**直接作废**；仅对 5.x/6.x 老版本成立（`pyJianYingDraft` 的适用区间）。

### 2.6 四道硬墙

| # | 墙 | 证据 | 后果 |
|---|---|---|---|
| 1 | **法务** | 闭源商业软件，安装目录无任何再分发/衍生授权文件；EULA 禁止反向工程与二次分发 | 内嵌 DLL = 侵权 + 无法过合规 |
| 2 | **ABI** | 只有运行时 DLL，无 `.lib`/`.h`/IDL；导出符号未公开 | 无法静态链接，只能 `LoadLibrary` 赌符号名，版本一变就崩 |
| 3 | **演进** | 11.6.0 与上一版 DLL 名/布局随时变；草稿格式已从明文改密文 | 每次客户端更新都是一次断裂 |
| 4 | **数据** | v11 草稿加密，密钥在原生侧 | 无法做数据交换，也无法迁移存量工程 |

> 一句话：**剪映的"内核"不是一个组件，是一台封闭机器。** 能用它的方式只有一种——让人在它的界面里操作。

### 2.7 能借鉴的（且已经写进计划文档的部分）

不复用代码，但这些设计值得抄：

- **微秒时间基 + `target_timerange`/`source_timerange` 分离**（素材内偏移与时间线位置解耦）——已写入计划 4.1 数据模型 v2。
- **materials 资源池 + `extra_material_refs` 引用**（同一素材被多片段引用，只存一份）——已写入。
- **导出预设的分组方式**（分辨率/码率/帧率/平台）——已写入 UI 方案 5.3。
- **交互**：轨道头吸附、磁性时间线、波纹编辑的视觉反馈——已进设计稿 `clip-editor-v2.html`。

## 3. OpenCut Classic 解剖

源码：`C:\Users\lrp\rea-install\analysis\opencut-classic`（`OpenCut-app/opencut-classic`）。

### 3.1 许可与可自托管

| 项 | 事实 |
|---|---|
| LICENSE | **MIT**（`Copyright 2025-2026 OpenCut`，标准 MIT 全文，无商用限制附加条款） |
| README 自托管 | 有 `Self-Hosting with Docker` 章节 + `docker-compose.yml` |
| 技术栈 | Next.js 16 + React 19 + zustand + **Rust/WASM 合成器** + mediabunny |
| 规模 | 716 个 `.ts/.tsx/.rs` 文件 |

MIT + 可自托管 = **法务上完全可复用**，这是与剪映的根本差别。

### 3.2 模块规模与 React 耦合（决定"能不能只换内核"）

| 目录 | 文件 | 行数 | 含 React 文件 | 性质 |
|---|---|---|---|---|
| `core/` | 13 | 4,009 | **0** | 管理器（时间线/播放/渲染/保存/选区/命令） |
| `commands/` | 53 | 4,006 | **0** | 命令对象（可撤销） |
| `params/` | 3 | 790 | **0** | 参数注册表 |
| `animation/` | 17 | 3,370 | **0** | 关键帧求值 |
| `masks/` | 25 | 7,071 | 2 | 遮罩几何/SDF/羽化 |
| `retime/` | 8 | 398 | 0 | 变速 |
| `ripple/` | 4 | 377 | 0 | 波纹编辑 |
| `rendering/` `export/` | 5 | 228 | 0 | 渲染/导出元数据 |
| **内核小计** | **128** | **≈20,200** | **2** | **可移植** |
| `components/` | 86 | 10,898 | **59** | React UI |
| `timeline/` | 105 | 16,870 | **33** | React 交互层 |
| `preview/` | 24 | 5,463 | 10 | React 预览 |
| `selection/` | 13 | 1,035 | 5 | React 选区 |
| `hooks/` | 9 | 277 | 9 | React hooks |
| **UI 小计** | **237** | **≈34,500** | **116** | **必须重写** |

**关键比例：内核 37%，UI 63%。**

也就是说，"直接用内核 + UI 做适配改造"里，**UI 那部分是工作量的大头，而且是重写不是适配**——React 的 hooks/context 无法在 Vue 里"适配"，只能改写为 composable。

内核层唯一的外部耦合是 3 处 `sonner`（React toast 库）和 1 处 `import type`——都是几十行可替换的噪音，不构成障碍。

### 3.3 真正的宝贝：`opencut-wasm`

这是整个评估里最有价值的一条：**OpenCut 把渲染内核抽成了独立 npm 包，不需要它整个编辑器就能用。**

| 项 | 事实 |
|---|---|
| 包名/版本 | `opencut-wasm@0.2.10` |
| 许可 | MIT（`rust/wasm/Cargo.toml` 明确 `license = "MIT"`） |
| 后端 | **wgpu**：WebGPU 优先，**WebGL 回退**（`supports_surface_rendering()` 分支） |
| 导出函数 | 6 个：`initCompositor`、`resizeCompositor`、`getCompositorCanvas`、`uploadTexture`、`releaseTexture`、`renderFrame` |

**帧描述符（`rust/crates/compositor/src/frame.rs`）** —— 这是一个通用场景图，与我们的模型高度同构：

```rust
FrameDescriptor { width, height, clear: { color }, items: Vec<FrameItemDescriptor> }

FrameItemDescriptor =
  | Layer(LayerDescriptor)
  | SceneEffect { effect_pass_groups }

LayerDescriptor {
  texture_id: String,
  transform: { center_x, center_y, width, height, rotation_degrees, flip_x, flip_y },
  opacity: f32,
  blend_mode: BlendMode,
  effect_pass_groups: Vec<Vec<EffectPassDescriptor>>,
  mask: Option<{ texture_id, feather, inverted }>,
}
```

对照我们现在的 `compositor.js`：

| 我们的能力 | FrameDescriptor 对应 | 差距 |
|---|---|---|
| `computeElementBox`（x/y/w/h/rotation） | `transform` | **1:1** |
| 不透明度 | `opacity` | 1:1 |
| 矩形/椭圆/贝塞尔遮罩 + 羽化 + 反相 | `mask{ texture_id, feather, inverted }` | 遮罩要先栅格化成纹理（我们本来就在 `masks.js` 里画） |
| 片段模糊 `blur` | `effectPassGroups`（shader + uniforms） | 从"画布 filter"升级为 shader pass |
| 无 | `blend_mode` | **白送**：正片叠底/滤色/叠加等 |
| 无 | `SceneEffect` | **白送**：整场景调色 pass |

**结论：把我们的 `compositor.render()` 改成"构建 FrameDescriptor → 调 `renderFrame`"，是映射工作，不是重写。** 预计 200–350 行映射层 + 纹理生命周期管理。

### 3.4 但它有两个与我们错位的地方

| 维度 | OpenCut | 我们 | 影响 |
|---|---|---|---|
| 工程存储 | **IndexedDB + OPFS**（浏览器本地） | 服务端 SQLite（多端一致、可备份） | 若 L1/L2 需自写 `StorageAdapter` 接我们的 API；**L0 不受影响** |
| 导出 | **浏览器内** mediabunny + WebCodecs 封装 | **服务端 ffmpeg**（`adelay/amix/atrim` 多轨混音、10 分钟长任务） | 若 L2 则导出链路整体搬到浏览器，长片/多轨音频会退化；**L0 不受影响**（我们仍从画布取帧传服务端） |

这两条是"整块替换"路线最疼的地方，也是我建议先做 L0 的原因。

## 4. 四种粒度对比

| 维度 | **L0 只换渲染器** | **L1 内核移植** | **L2 整块替换** | **L3 只借架构** |
|---|---|---|---|---|
| 拿什么 | `opencut-wasm` | core+commands+params+animation+渲染器 | 整个 `apps/web` | 无代码 |
| 保留我们的 | 模型/UI/命令栈/服务端导出 | UI/服务端/素材库 | 仅壳与素材注入 | 全部 |
| 新增代码 | 映射层 ~300 行 + 纹理管理 | 适配层 ~3–5k 行 + Vue 化交互 | 宿主适配 ~2k 行 + 主题改造 | — |
| 要重写的 | 无 | `timeline/` 33 个 React 文件 → composable（≈17k 行） | 设计稿全部作废 | 按计划 Phase1/2 |
| 周期 | **2–3 周** | 3–4 个月 | 6–8 周（但丢设计） | 3 个月+ |
| 收益 | GPU 合成、blend mode、shader 特效、帧率提升 | +命令栈/参数注册表/时间量化 | 最快拿到完整功能 | 无依赖 |
| 风险 | 低（可开关回退） | 中高（模型迁移+UI 重写并行） | 高（设计/体验全丢，导出退化） | 低 |
| 与现有设计稿 | **完全兼容** | 兼容（字段要重绑） | 作废 | 兼容 |

## 5. 推荐路线：先 L0，用数据决定要不要 L1

### 5.1 L0 落地设计

```text
store.js  (不动)
   ↓  project + time
compositor-adapter.js  (新增，~300 行)
   ├─ toFrameDescriptor(project, time)  → 复用现有 computeElementBox / keyframes / masks
   ├─ texturePool: map<clipId|mediaId, textureId>
   │     video:  <video> currentTime → createImageBitmap → uploadTexture
   │     image:  ImageBitmap → uploadTexture
   │     text:   离屏 Canvas2D 绘制 → createImageBitmap → uploadTexture
   │     mask:   masks.js 画到灰度图 → uploadTexture
   ↓
opencut-wasm.renderFrame(descriptor) → getCompositorCanvas()
   ↓
预览：把该 canvas 贴到 EditorPreview
导出：从该 canvas toBlob('image/jpeg') → 现有 /export/frame 上传（服务端 ffmpeg 不变）
```

三个必须做的工程决策：

1. **开关**：`?renderer=wasm|canvas2d`，读不到 WebGPU/WebGL 或有异常时自动回落现有 Canvas2D。现有 `compositor.js` 保留一整个版本周期。
2. **纹理生命周期**：`uploadTexture` 是显式资源。必须按 `(clipId, sourceTimeBucket)` 做 LRU + `releaseTexture`，否则显存爆。现有 `audioBufferCache` 泄漏的教训在这里会重演，而且更贵。
3. **文字与遮罩先栅格化**：不要试图用 shader 重画文字。`drawText` 与 `masks.js` 原样保留，输出成纹理即可——这也保证视觉零回归。

### 5.2 验收基准（决定要不要继续）

| 指标 | 现状（Canvas2D） | L0 目标 |
|---|---|---|
| 1080p/30fps 预览帧率 | 目测 20–30，多轨掉帧 | **≥ 55** |
| 4 轨 + 2 遮罩 + 1 模糊 | 明显掉帧 | ≥ 45 |
| 导出 60s 片段耗时 | 现状基线待测 | **不慢于现状**（取帧多一次 GPU 读回） |
| 视觉一致性 | — | 逐帧 PSNR ≥ 40 dB（文字/遮罩不得偏移） |
| 内存 | — | 峰值不高于现状 +20% |

### 5.3 什么情况下升级到 L1

只有当 L0 跑完、且满足**至少两条**时，才值得移植内核：

- 需要**帧精确**编辑（时间量化），而自研 controllers 反复出 bug；
- 需要**多选/批量/波纹/滑移**等结构化操作，命令栈成为瓶颈；
- L0 后仍频繁出现"状态与画面不一致"类 bug（说明模型层是瓶颈，不是渲染层）。

否则，L1 花 3–4 个月换来的主要是"架构更漂亮"，用户感知不到。

### 5.4 明确不推荐的：L2

把整个 `apps/web` 当编辑器用，技术上可行（MIT + Docker 自托管），但那等于：

- 上一轮做的两份 UI 设计稿（`clip-editor-v2.html`、`create-param-v2.html`）全部作废；
- 导出从服务端 ffmpeg 退回浏览器 WebCodecs，**长片、多轨混音、11 分钟以上工程会退化**；
- 工程存储从服务端 SQLite 变 IndexedDB，**多端/备份/协作全丢**；
- 素材库与成品架的联动要重写。

除非目标是"两周内上线一个能用的剪辑器"，否则不划算。

## 7. 风险清单

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| `opencut-wasm` 版本漂移（0.2.x） | 中 | 中 | 锁版本 + 把 `.wasm` 与 `.d.ts` vendored 进仓库，不跟随上游 |
| WebGPU 在目标机器不可用 | 低 | 中 | 它自带 WebGL 回退；再不行回落 Canvas2D |
| 纹理上传成为新瓶颈（每帧 `createImageBitmap`） | 中 | 高 | 按 `(mediaId, 时间桶)` 缓存 ImageBitmap；静态图只传一次 |
| 视觉回归（文字/遮罩偏移） | 中 | 高 | 建立 PSNR 对比脚本，逐帧比对旧实现 |
| 引入 WASM 后包体增大 | 高 | 低 | 动态 `import()`，仅在进入剪辑页时加载 |
| 团队不熟悉 Rust/wgpu | 中 | 中 | L0 不需要改 Rust，只调 JS API；出问题按 issue 上报而非自修 |
