## 五、合并建议

### 推荐顺序（共 4 步，1 次真正的合并，0 次冲突）

**Step 0 — 先固化工作区（必需，不能跳过）**

```bash
# 方案 A：提交
git add -A && git commit -m "wip: 2026-10-21 工作区快照"
# 方案 B：暂存
git stash push -u -m "wip-20261021"
# 方案 C：另开工作树，不碰当前目录
git worktree add ../mls-merge master
```

**Step 1 — `master` 快进到 `fix/audit-20261020`（零冲突）**

```bash
cd ../mls-merge            # 若用方案 C
git checkout master
git merge --ff-only fix/audit-20261020
```

理由：冲突预检退出码 0，且 `master` 是 fix 的祖先，`--ff-only` 是最安全的形态（失败即说明有人动过分支，此时应立即停下重新预检）。合并后 `master` = `debf247`，同时把原本未推送的 `251e429` 一并带上。

**Step 2 — 本地验证后再推送**

```bash
npm test                   # 或 node test/suite.js，按仓库既有脚本
git log --oneline -3
git push origin master     # 推送前请自行确认，这一步会改变远程状态
```

**Step 3 — `backup-pre-rollback` 归档，不合并**

```bash
git tag archive/pre-rollback-20261021 backup-pre-rollback
git branch -D backup-pre-rollback          # 打 tag 之后再删才安全
```

### 为什么 backup-pre-rollback 不值得保留为分支

- 它是**回滚前的快照**，不是功能分支：整条支线只有 1 个提交 `e879c3f`，内容是"把整个 `editor/`（含 4064 个构建产物）+ 一批设计文档一次性提交"，提交信息只是"修复后提交"，没有任何后续演进。
- 它落后 `master` 4 个提交，独有内容已被 `master` 的 `878104f`（剥离构建产物、脱敏账号）取代；同名文件逐个比对全部 DIFF，属于**被取代的旧版本**，不是"另一条还没合的特性"。
- 任何一次合并都会产生 1076~1084 个冲突，其中 99% 是 `editor/apps` 下的 add/add——这是构建产物目录，人工解冲突毫无意义。
- 保留价值只在"万一回滚后要找回旧文件"。用轻量 tag 或 `git bundle` 归档即可，占的是对象库空间，不像分支那样出现在 `git branch` 里误导后续操作。
